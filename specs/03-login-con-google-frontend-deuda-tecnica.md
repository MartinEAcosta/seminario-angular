# Deuda técnica — Spec 03: Login con Google (wiring del frontend, code flow)

**Spec original:** specs/03-login-con-google-frontend.md
**Implementado en:** commit 27d552a (PR #18, merge a2db1cd)

## Resumen

La implementación cubre el flujo feliz (popup → code → POST backend → `handleAuthSuccess`), pero diverge del plan de la spec en varios puntos no documentados: cambia el endpoint, introduce una abstracción (`AUTH_PROVIDER`) que rompe el patrón `Observable + subscribe` que la propia spec pedía reutilizar, y deja sin cumplir casi todos los criterios de aceptación relacionados con manejo de errores (toast en 404, silencio en cancelación voluntaria). Además, el commit mezcla cambios no relacionados y deja tests existentes rotos a nivel de inyección de dependencias.

## Hallazgos

- **[Severidad: alta]** Mismatch endpoint spec vs. código: la spec documenta `POST {apiURL}auth/google` (specs/03-login-con-google-frontend.md:46) como el contrato que debe implementar `udemix-backend`. El código real pega a `POST {apiURL}auth/login/google` — `src/app/auth/services/auth.service.ts:48` (`this.http.post<AuthResponse>(\`${this.baseURL}/login/google\`, { code })`), con `baseURL` definido como `${environment.apiURL}auth` en `auth.service.ts:24`. Quien implemente el backend siguiendo la spec al pie de la letra construirá el endpoint equivocado.

- **[Severidad: alta]** El toast de error en fallos HTTP (404, etc.) nunca se dispara, violando el criterio de aceptación de la spec ("si el backend no responde (404)... se muestra un toast de error vía UIService", specs:62). Causa raíz en `auth.service.ts:53`: `catchError( (error: any) => { console.log(error); return this.handleAuthError( error.error ) } )` pasa `error.error` (el *body* de la respuesta) en vez del `HttpErrorResponse` completo. `handleAuthError` (`auth.service.ts:185-197`) decide el toast leyendo `error.status` (línea 192) — que en este camino siempre es `undefined` porque se le pasó el body, no la respuesta. Resultado: ningún código HTTP (400, 404, 500...) dispara nunca el toast ni el logout vía este flujo.

- **[Severidad: alta]** No hay ningún toast cuando el script de Google falla en cargar. La spec exige mostrar un toast vía `UIService` en ese caso (specs:27, 62). El único manejo existente es `this.authService.prepareGoogle().catch( err => console.error('Error preparando Google Auth', err) )` en `form-login.component.ts:41` — solo loguea en consola, nunca llama a `UIService.showToastMessage`.

- **[Severidad: media-alta]** El criterio "si el usuario cierra el popup sin completar, no se muestra ningún error en consola" (specs:63) no se cumple: el handler de error del provider en el constructor de `AuthService` hace `err => console.warn('Login cancelado o fallido', err)` sin excepción (`auth.service.ts:42`). No existe en ningún archivo una rama que compare `err === 'popup_closed'` (o `err.type === 'popup_closed'`, como pedía la spec en el paso 1 del implementation plan, specs:53) para omitir el log en ese caso específico. `GoogleAuthService` sí propaga `err.type` tal cual (`google-auth.service.ts:29`), pero nadie lo inspecciona del lado de `AuthService`.

- **[Severidad: media-alta]** Desvío arquitectónico no documentado: `auth.provider.ts` (archivo nuevo, no mencionado en la spec). El plan de implementación de la spec (paso 1, specs:53) especifica inyectar `GoogleAuthService` directamente en `AuthService` y que `loginWithGoogle` sea `Observable<User | false>`. El código real introduce una interfaz `AuthProvider` + `InjectionToken AUTH_PROVIDER` (`auth.provider.ts:3-10`), cableada en `app.config.ts` vía `{ provide: AUTH_PROVIDER, useExisting: GoogleAuthService }`, y cambia `loginWithGoogle` para que devuelva `void` (`auth.service.ts:59-61`) en vez de `Observable<User | false>`. Esto rompe el patrón homogéneo que `loginUser`/`registerUser` siguen (`auth.service.ts:63-71`, `73-84`: devolver Observable, el componente se suscribe y navega) — patrón que la spec explícitamente decía reutilizar (specs:18, 71). Hoy no existe un segundo `AuthProvider` real (GitHub de SPEC 02 sigue sin wiring), por lo que la abstracción no tiene ningún consumidor que la justifique — posible over-engineering sin caso de uso, y sin ninguna nota de diseño que explique por qué se adoptó.

- **[Severidad: alta]** Pérdida de control de flujo en el componente: `onLoginWithGoogle` (`form-login.component.ts:59-61`) solo llama a `authService.loginWithGoogle()` (que a su vez solo dispara `provider.signIn()`, abriendo el popup) sin suscribirse a nada. La navegación tras éxito ocurre dentro de `AuthService.exchangeCode` (`auth.service.ts:50-52`, `this.router.navigateByUrl('')`), registrada como side-effect permanente en el constructor del singleton `AuthService` (`auth.service.ts:39-44`), no como reacción al click. Esto contrasta con `onLogin()` (`form-login.component.ts:44-57`), que sí se suscribe al Observable y navega desde el propio componente. El componente queda sin ninguna visibilidad sobre el resultado de su propio botón.

- **[Severidad: media]** Orden de operaciones riesgoso en `exchangeCode`: `this.router.navigateByUrl('')` se ejecuta (`auth.service.ts:51`) **antes** de `this.handleAuthSuccess(authResponse)` (línea 52), es decir, la navegación se dispara antes de que `UserState.setUser/setToken/setAuthStatus` se actualicen. Funciona hoy por timing (los setters síncronos corren antes de que el router resuelva sus guards), pero es un orden implícito y frágil, no una garantía de diseño — cualquier guard que lea el estado de auth de forma síncrona durante la navegación podría ver el estado viejo.

- **[Severidad: media]** Imports muertos que delatan una migración incompleta: `GoogleAuthService` se importa pero nunca se usa en `form-login.component.ts:10` (el componente solo usa `AuthService`, no `GoogleAuthService`) y en `auth.service.ts:9` (`AuthService` solo usa el token `AUTH_PROVIDER`, no la clase concreta). Son residuos de una versión anterior del código donde probablemente se inyectaba `GoogleAuthService` directamente, antes de introducir el token.

- **[Severidad: media]** El script del SDK de Google se carga dos veces por cada visita a `/auth/login`. `src/index.html:13` agrega un `<script src="https://accounts.google.com/gsi/client" async defer>` estático — cambio no mencionado en ningún paso del implementation plan de la spec (que solo hablaba de `auth.service.ts`, `form-login.component.ts/html`). Además, `GoogleAuthService.prepare()` (`google-auth.service.ts:19-38`) crea dinámicamente **otro** `<script>` con la misma URL y lo inyecta en `document.head`. Ambas cargas son redundantes entre sí.

- **[Severidad: media]** Import de environment incorrecto en `google-auth.service.ts:2`: `import { environment } from '../../../environments/environment.development';` apunta explícitamente al archivo de desarrollo, en vez del alias estándar `../../../environments/environment` que usa el resto del código (p. ej. `auth.service.ts:7`) y que Angular reemplaza en build de producción vía `fileReplacements` (ver CLAUDE.md). Hoy no causa bug visible porque `GOOGLE_CLIENT_ID` tiene el mismo valor en `environment.ts` y `environment.development.ts`, pero es un bug latente: si alguna vez difieren, el build de producción seguiría usando el client ID de desarrollo.

- **[Severidad: alta]** Tests existentes rotos a nivel de inyección de dependencias, y sin cobertura real del flujo nuevo. `auth.service.spec.ts` (`TestBed.configureTestingModule({})` + `TestBed.inject(AuthService)`) y `form-login.component.spec.ts` (`imports: [FormLoginComponent]`, que instancia `AuthService` transitivamente) no fueron tocados por este commit. `AuthService` ahora inyecta `AUTH_PROVIDER` en su constructor (`auth.service.ts:26`, usado en `auth.service.ts:39-44`), y `AUTH_PROVIDER` (`auth.provider.ts:10`) no tiene `providedIn` por defecto — solo se provee en `app.config.ts` vía `useExisting: GoogleAuthService`, que no forma parte de ningún `TestBed.configureTestingModule`. Por construcción, ambos specs deberían lanzar `NullInjectorError: No provider for AUTH_PROVIDER` en cuanto Angular intenta instanciar `AuthService`. (Intenté confirmar esto corriendo `ng test --watch=false`, pero la suite completa falla en compilar por errores preexistentes no relacionados en otros specs del repo — `btn-add-to-cart`, `search-bar`, `about-page`, `explore-page`, `pagination.service`, etc. — que impiden ejecutar Karma; el análisis de DI de arriba es estático pero se desprende directamente de leer ambos archivos.) El nuevo `google-auth.service.spec.ts` solo verifica `should be created`, sin cubrir `prepare()`, `signIn()`, `onCode()` ni el manejo de `popup_closed`. No existe ningún spec para `auth.provider.ts`.

- **[Severidad: baja]** Metadata de proceso desactualizada: el header de la spec sigue en `> **Status:** Aprobado` (specs/03-login-con-google-frontend.md:3) a pesar de estar mergeada en `main` desde PR #18 (merge `a2db1cd`). Debería decir "Implementado", como ya hace `specs/02-botones-google-github-login.md:3`.

- **[Severidad: baja, informativo]** Scope creep en el commit 27d552a: además de los archivos de la spec, el commit toca `app.config.ts` (elimina `importProvidersFrom(BrowserModule, ReactiveFormsModule)`), agrega `.claude/settings.json` y `.vscode/settings.json`, y modifica 7 componentes sin relación con Google login (`category-select.component.ts`, `course-detail.component.ts`, `course.service.ts`, `btn-remove.component.ts`, `card-action.component.ts`, `publish-status-menu.component.ts`, `vjs-player.component.ts`, `about-page.ts`, `teacher-request-form.component.ts`). Mezclar esto en un commit de feature dificulta el review y el revert selectivo.

- **[Confirmado — alcance intencional, no deuda nueva]** El botón de Google en `src/app/auth/components/form-register/form-register.component.html:48` sigue sin atributo `(click)`. Esto es consistente con el "Out of scope" explícito de la spec (specs:33), no es una omisión accidental. Queda como trabajo pendiente real para una spec futura si se decide implementarlo.

- **[Confirmado — decisión documentada, no deuda]** No hay estado de carga/disabled en el botón de Google mientras se resuelve el popup + el intercambio con el backend. Esto es una decisión explícita de la spec (specs:73), no un desvío.

## Recomendaciones

- Resolver el mismatch de endpoint: decidir si el contrato correcto es `/auth/login/google` (código actual) o `/auth/google` (spec), actualizar el que esté desactualizado, y dejarlo documentado antes de implementar el endpoint en `udemix-backend`.
- Corregir `exchangeCode` para pasar el `HttpErrorResponse` completo a `handleAuthError` (no `error.error`), y agregar el toast faltante en el catch de `prepareGoogle()` en `form-login.component.ts:41`.
- Diferenciar explícitamente `err === 'popup_closed'` en el handler de error de `AuthService` (constructor, `auth.service.ts:42`) para cumplir el criterio de "no mostrar nada si el usuario cancela voluntariamente".
- Revisar si `AUTH_PROVIDER`/`auth.provider.ts` se justifica: si no hay un plan concreto de un segundo proveedor (GitHub u otro) en el corto plazo, considerar volver a inyectar `GoogleAuthService` directamente y devolver `Observable<User | false>` desde `loginWithGoogle`, como pedía la spec original, para no romper el patrón homogéneo de la clase. Si se decide mantener la abstracción, documentarla (aunque sea retroactivamente) y limpiar los imports muertos de `GoogleAuthService` en `form-login.component.ts` y `auth.service.ts`.
- Agregar un provider de `AUTH_PROVIDER` en los specs existentes (o darle un valor por defecto) para que `auth.service.spec.ts` y `form-login.component.spec.ts` no rompan por `NullInjectorError`, y escribir tests reales para `exchangeCode`, `loginWithGoogle`, y `GoogleAuthService.prepare/signIn/onCode` (incluido el camino `popup_closed`).
- Eliminar la carga duplicada del script de Google: quedarse solo con la inyección dinámica vía `prepare()` (que ya controla el signal `ready`) o solo con el `<script>` estático de `index.html`, no ambos.
- Cambiar el import de `environment` en `google-auth.service.ts:2` al alias estándar (`../../../environments/environment`) para que respete `fileReplacements` en build de producción.
- Actualizar el header de `specs/03-login-con-google-frontend.md` de "Aprobado" a "Implementado".
- En futuros commits de feature, evitar mezclar cambios de configuración de editor/IDE o refactors sin relación con el commit de la feature, para mantener el historial auditable y revertible.
